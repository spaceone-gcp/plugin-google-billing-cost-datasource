# 성능 최적화 가이드 (v2.0)

## 개요

이 문서는 Google Cloud Billing 플러그인 v2.0에서 성능 최적화를 위한 방법론과 가이드라인을 제공합니다. v2.0에서는 gRPC 스마트 청킹, Credits Detail 모드, Cost 필드 보장 시스템 등 새로운 최적화 기법이 도입되었습니다.

## v2.0 성능 최적화 방법론 ⭐ **UPDATED**

###  v2.0 핵심 원칙
- **gRPC 스마트 청킹**: 동적 배치 크기 조정으로 대용량 데이터 안정 전송 ⭐ **NEW**
- **Cost 필드 100% 보장**: 5단계 보장 시스템으로 성능 저하 없이 무결성 확보 ⭐ **NEW**
- **Credits Detail 최적화**: 필요시에만 상세 모드 활성화로 성능 균형 ⭐ **NEW**
- **통합 Source 기반**: 단일 진입점으로 라우팅 최적화 ⭐ **NEW**
- **과학적 표기법 지원**: 극소값 처리 최적화로 데이터 손실 방지 ⭐ **NEW**

###  v2.0 성능 균형점
```
v2.0 성능 = f(gRPC최적화, 데이터보장, Source통합) = 안정성 + 처리속도 + 메모리효율성
```

v2.0에서는 데이터 무결성을 보장하면서도 최적의 성능을 달성합니다.

#### v2.0 성능 향상 요소 ⭐ **NEW**
- **gRPC 청킹**: 메시지 크기 자동 조정 (4MB → 16MB 제한 대응)
- **스마트 배치**: 데이터 크기에 따른 동적 배치 크기 (기본값: 5)
- **세션 캐싱**: GCS 인증 세션 재사용으로 연결 오버헤드 감소
- **중복 요청 방지**: RequestDeduplicator로 불필요한 처리 제거

#### v2.0 안정성 확보 요소 ⭐ **NEW**
- **5단계 보장**: Cost 필드 누락 0% 달성
- **예외 격리**: 개별 커넥터 실패가 전체 시스템에 미치는 영향 차단
- **동시성 제어**: 파일별 락 관리로 데이터 무결성 보장
- **실시간 검증**: gRPC 응답 전 최종 데이터 검증

###  v2.0 핵심 최적화 기법

#### 1. gRPC 스마트 청킹 시스템 ⭐ **NEW**
```python
class GRPCSmartChunking:
    """v2.0 gRPC 스마트 청킹 최적화"""
    
    def __init__(self):
        self.default_batch_size = 5          # 최적화된 기본 배치 크기
        self.max_message_size = 16 * 1024 * 1024  # 16MB 제한
        self.adaptive_sizing = True          # 동적 크기 조정
    
    def optimize_batch_size(self, data_size: int, record_count: int) -> int:
        """데이터 크기에 따른 배치 크기 자동 조정"""
        if data_size > 10 * 1024 * 1024:     # 10MB 이상
            return 2                         # 작은 배치
        elif data_size > 5 * 1024 * 1024:    # 5MB 이상
            return 3                         # 중간 배치
        else:
            return 5                         # 기본 배치
    
    def chunk_data(self, data: List[dict]) -> Generator[List[dict], None, None]:
        """스마트 청킹으로 데이터 분할"""
        estimated_size = self._estimate_data_size(data)
        batch_size = self.optimize_batch_size(estimated_size, len(data))
        
        for i in range(0, len(data), batch_size):
            yield data[i:i + batch_size]
```

#### 2. Cost 필드 5단계 보장 시스템 ⭐ **NEW**
```python
class CostFieldGuaranteeSystem:
    """Cost 필드 100% 보장 시스템"""
    
    # 1단계: main.py - gRPC 응답 전 최종 검증
    def final_cost_validation(self, response_data: List[dict]) -> List[dict]:
        """최종 gRPC 응답 전 cost 필드 검증"""
        for record in response_data:
            if 'cost' not in record or record['cost'] is None:
                # 긴급 복구: 0.0으로 설정하고 로그 기록
                record['cost'] = 0.0
                self._log_cost_recovery(record)
        return response_data
    
    # 2단계: cost_manager.py - BigQuery 응답 생성 시
    def ensure_cost_in_bigquery_response(self, df) -> pd.DataFrame:
        """BigQuery 응답에서 cost 필드 보장"""
        if 'cost' not in df.columns:
            df['cost'] = 0.0
        df['cost'] = df['cost'].fillna(0.0)
        return df
    
    # 3단계: field_mapper.py - 필드 매핑 시
    def ensure_cost_in_mapping(self, mapped_data: dict) -> dict:
        """필드 매핑 결과에서 cost 필드 보장"""
        if 'cost' not in mapped_data:
            mapped_data['cost'] = 0.0
        return mapped_data
    
    # 4단계: 모든 parser - 파일 파싱 시
    def ensure_cost_in_parsed_data(self, parsed_record: dict) -> dict:
        """파싱된 데이터에서 cost 필드 보장"""
        if 'cost' not in parsed_record:
            # 과학적 표기법 지원
            cost_candidates = ['amount', 'total', 'charge']
            for candidate in cost_candidates:
                if candidate in parsed_record:
                    parsed_record['cost'] = self._parse_scientific_notation(
                        parsed_record[candidate]
                    )
                    break
            else:
                parsed_record['cost'] = 0.0
        return parsed_record
    
    # 5단계: BigQuery SQL - 쿼리 레벨에서
    def get_cost_guaranteed_sql(self) -> str:
        """Cost 필드를 보장하는 SQL"""
        return """
        SELECT 
            COALESCE(cost, 0.0) as cost,  -- NULL 방지
            COALESCE(CAST(cost AS FLOAT64), 0.0) as cost,  -- 과학적 표기법 지원
            *
        FROM billing_table
        WHERE cost IS NOT NULL OR cost = 0  -- 완전한 데이터만 선택
        """
```

#### 3. Credits Detail 모드 최적화 ⭐ **NEW**
```python
class CreditsDetailOptimization:
    """Credits Detail 모드 성능 최적화"""
    
    def __init__(self):
        self.credits_detail_cache = {}       # 크레딧 정보 캐싱
        self.batch_optimization = True       # 배치 최적화 활성화
    
    def optimize_credits_query(self, credits_detail_mode: bool) -> str:
        """Credits Detail 모드에 따른 쿼리 최적화"""
        if credits_detail_mode:
            # 상세 모드: GROUP BY 없이 원본 데이터 조회
            return self._get_detailed_credits_sql()
        else:
            # 기본 모드: GROUP BY로 집계하여 성능 최적화
            return self._get_aggregated_credits_sql()
    
    def _get_detailed_credits_sql(self) -> str:
        """Credits Detail을 위한 원본 데이터 SQL"""
        return """
        SELECT 
            cost,
            credits,  -- 원본 크레딧 배열 보존
            -- ... 모든 필드 보존
        FROM billing_export
        WHERE cost IS NOT NULL
        ORDER BY usage_start_time DESC
        """
    
    def _get_aggregated_credits_sql(self) -> str:
        """성능 최적화된 집계 SQL"""
        return """
        SELECT 
            SUM(cost) as cost,
            ARRAY_AGG(credits IGNORE NULLS) as credits_summary,
            -- ... 집계된 필드들
        FROM billing_export
        WHERE cost IS NOT NULL
        GROUP BY project_id, service_description
        ORDER BY cost DESC
        """
```

#### 기본 순차 처리 패턴
```python
class OptimizedSequentialManager:
    """순차 처리 최적화 매니저"""
    
    def collect_resources(self, params):
        """
        순차적 리소스 수집
        """
        reset_state_counters()
        
        # 서비스별 순차 처리
        for service_type in self.service_types:
            try:
                resources = self._collect_service_resources(service_type, params)
                for resource in resources:
                    yield BaseResponse.create_with_logging(resource)
            except Exception as e:
                _LOGGER.error(f"Failed to collect {service_type}: {e}")
                yield ErrorResourceResponse.create_with_logging(
                    e, service_type, "Resource"
                )
        
        # 수집 결과 요약
        log_state_summary()

    def _collect_service_resources(self, service_type, params):
        """서비스별 리소스 수집 (순차 처리)"""
        regions = self._get_available_regions()
        all_resources = []
        
        for region in regions:
            try:
                # 리전별 순차 처리
                resources = self._collect_region_resources(region, service_type, params)
                all_resources.extend(resources)
                
                _LOGGER.info(
                    f" Collected {len(resources)} {service_type} resources from {region}"
                )
            except Exception as e:
                _LOGGER.warning(f"Failed to collect from {region}: {e}")
                continue
                
        return all_resources
```

###  성능 측정 및 모니터링

#### 핵심 메트릭
- **처리 시간**: 전체 수집 완료 시간
- **메모리 사용량**: 최대 메모리 사용량
- **API 호출 수**: 총 API 호출 횟수
- **성공률**: 성공한 리소스 수집 비율
- **오류율**: 실패한 리소스 수집 비율

#### 모니터링 구현
```python
import time
import psutil
from typing import Dict, Any

class PerformanceMonitor:
    """성능 모니터링 클래스"""
    
    def __init__(self):
        self.start_time = None
        self.start_memory = None
        self.api_call_count = 0
        
    def start_monitoring(self):
        """모니터링 시작"""
        self.start_time = time.time()
        self.start_memory = psutil.Process().memory_info().rss
        
    def record_api_call(self):
        """API 호출 기록"""
        self.api_call_count += 1
        
    def get_performance_summary(self) -> Dict[str, Any]:
        """성능 요약 반환"""
        current_time = time.time()
        current_memory = psutil.Process().memory_info().rss
        
        return {
            "total_time": current_time - self.start_time,
            "memory_usage_mb": (current_memory - self.start_memory) / 1024 / 1024,
            "api_calls": self.api_call_count,
            "avg_api_time": (current_time - self.start_time) / max(self.api_call_count, 1)
        }
```

## 모범 사례

###  권장 사항

1. **순차 처리 우선**
   - 안정성과 메모리 효율성을 위해 순차 처리 방식 채택
   - 복잡도 감소로 디버깅과 유지보수 용이성 확보

2. **효율적인 API 사용**
   - 배치 API와 페이징을 활용한 최적화
   - 불필요한 API 호출 최소화

3. **메모리 관리**
   - 제너레이터 패턴으로 메모리 사용량 제한
   - 대용량 객체의 즉시 처리 및 해제

4. **예외 처리**
   - 개별 서비스 실패가 전체에 미치는 영향 최소화
   - 적절한 로깅과 함께 안정적인 예외 처리

###  피해야 할 사항

1. **과도한 복잡성**
   - 불필요한 병렬 처리로 인한 복잡성 증가
   - 메모리 부족 위험성 증가

2. **비효율적인 API 사용**
   - 개별 API 호출의 과도한 사용
   - 타임아웃 설정 누락

3. **메모리 누수**
   - 대용량 객체의 장시간 보관
   - 캐시 크기 제한 없는 무제한 증가
